주문·결제 서버 모의 테스트

매장 주문을 받는 서버를 Kotlin·Spring Boot로 만들었습니다. 같은 주문이 두 번 들어올 때, 마지막 하나를 여러 명이 동시에 주문할 때, 결제 응답이 안 올 때 서버가 어떻게 처리하는지 눌러서 확인할 수 있습니다.

주문과 금액은 모두 예시 데이터입니다.

    동시 주문 테스트 결과 초과 판매
    
    
    재고가 1개일 때와 5개일 때, 24명이 동시에 주문하는 테스트를 잠금 방식 두 가지로 반복했습니다. 재고보다 많이 팔리면 '초과 판매'에 숫자가 찍힙니다. 0이면 정상입니다.
    
    
    잠금 방식재고반복초과 판매라운드별 판매 수종료 재고
    
  
    

  
    
    
    서버를 실제로 띄워 확인한 것 e2e
    
    
    서버, 모의 결제사, PostgreSQL, Redis, 메시지 브로커를 docker compose 로 띄우고 바깥에서 요청을 보내 확인한 결과입니다. 하루 정산과 결제사 거래 내역 대조도 여기서 확인했습니다.
    
    
      
  
      

  
      
    
      
      용어 풀이
      
      
        
      멱등 키
      요청마다 붙이는 이름표(Idempotency-Key). 같은 이름표가 또 오면 서버는 처음 결과를 그대로 돌려줍니다.
      
        
      낙관적 잠금
      잠그지 않고 진행하다가, 그 사이 다른 주문이 재고를 바꿨으면(버전이 달라졌으면) 다시 읽고 재시도하는 방식입니다.
      
        
      비관적 잠금
      재고를 먼저 잠그고 한 명씩 처리하는 방식입니다.
      
        
      아웃박스
      주문이나 결제를 바꿀 때 "알릴 내용"도 같은 DB 트랜잭션에 함께 적어 두고, 나중에 따로 전달하는 방식입니다. 주문은 바뀌었는데 알림만 사라지는 일이 없습니다.
      
        
      dead-letter
      여러 번 다시 시도해도 처리하지 못한 건을 버리지 않고 모아 두는 보관함입니다. 나중에 재처리 명령으로 다시 처리합니다.
      
        
      대사
      우리 기록과 결제사가 준 거래 내역 파일을 맞춰 보며 빠진 거래나 금액이 다른 거래를 찾는 일입니다.
